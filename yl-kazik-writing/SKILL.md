# 卡兹克机制型写作

## 共同写作约束（每次必读）

起稿前读取并执行 [写作公共约束](references/writing-foundation.md) 及其完整规则；直接调用本 Skill 也必须执行写前、写后和交付检查。它约束所有框架与风格，保护用户原话和有效修辞。下文或旧参考中的绝对词句禁令与它冲突时，以公共规则的语义裁决为准；脚本命中不能替代审稿。


这是维护者自制的 AI 科技文章引擎，研究对象为数字生命卡兹克的公开文章；不代表该作者制作、授权背书或参与维护。与 `yl-human-writing` 是两个独立方法，应单选主引擎，不叠加全部文风禁令。

运行要求：Python 3.10 或更新版本，仅使用标准库。完整来源和许可见 [SOURCE.md](SOURCE.md)。安装者语料、参考全文、CTA、截图、日志和成稿保存在 Skill 目录之外；笔记与图片服务均为可选接入。

把公开样本里有效的注意力、证据、叙事和节奏机制，转换成用户自己的文章。

写作目标不是“像某个人”，而是让读者感觉：

> 一个真正下场做事、掌握一手材料、敢于判断的人，正在把复杂技术讲给忙碌的普通人听。

用户的逐字稿、真实经历、业务判断和表达习惯，始终高于参考博主。

## 安装者表达校准

用户交回手调稿时，必须先与上一版逐处对照，学习修改的功能，不只摘几句口头禅。明显笔误和单篇题材词不进入稳定规则。

- 公众号保留短视频能传播的核心判断，但不照搬三秒口号。先用更成熟的措辞立住判断，再快速交代事件。
- 禁止用“我昨天发了视频”“上一篇文章”“播放量跑了多少”给文章垫背景。正文直接讲这件事。
- AI 产品稿优先沿“发生什么 → 新东西是什么 → 与主流有何不同 → 第一性原理 → 人话解释 → 动作背后的意义”推进，不把这条线拆成流水账式小标题。
- 技术讲清原理就停。普通人需要理解动作与格局，不需要被参数和名词淹没。
- 把历史暗示、商业案例和传播性概念融进同一条因果线；点到为止，不做逐项对标，不替读者把寓意讲完。
- 不代替读者说“谁是科技脊梁”“让人后背发凉”。让事实和力量对比自然形成共鸣。
- 少分节，一气呵成；只在正文切换成教程、清单或另一种阅读任务时使用小标题。
- 公众号默认不超过 1800 个中文非空白字符，2000 为硬上限。只有用户明确要求调查长文或更长篇幅时才突破。
- 用户定稿 Markdown 是唯一正文源。进入封面、HTML、归档或跨平台转换后，逐字继承，不自动修正疑似笔误。

## 一、先确认交付边界

开始前确认：

1. 文章对象和当前事件是什么？
2. 读者是谁，最终希望他改变什么判断或行动？
3. 最大字数、标题要求和固定结尾是什么？
4. 有哪些官方材料、原文、截图、X原帖和用户真实经历？
5. 当前只交付文字，还是已经明确“文字定稿”并允许做图、HTML或归档？

用户未指定长度时，根据任务选择：

- 即时热点、趋势、实测与方法稿：1200—1800字；
- 公众号文章默认不超过1800字，2000字为硬上限；
- 长篇调查只有在用户明确要求更长篇幅时例外，不机械追求4000—8000字。

长度要求优先于样本习惯。

## 二、选择文章原型

只选一个主原型，最多叠加一个副原型：

| 原型 | 核心承诺 | 主线 |
|---|---|---|
| 调查实验型 | 我替你亲自试过 | 好奇/困境 → 操作 → 踩坑 → 发现 → 结果 |
| 产品工作流型 | 这个变化少了哪些步骤 | 旧痛点 → 新操作 → 实际效果 → 限制 → 判断 |
| 现象趋势型 | 几条信号为什么属于同一件事 | 异常信号 → 时间线 → 阵营/利益 → 规则变化 |
| 人物故事型 | 技术如何改变一个具体的人 | 人物处境 → 技术介入 → 选择/代价 → 余味 |
| 方法商业型 | 我把跑通的方法交给你 | 真实问题 → 方法 → 失败点 → 可执行动作 |

没有亲测材料时，不选“调查实验型”，也不伪造“我试了”“我潜伏了”。

## 三、用HKRO决定是否动笔

写作前给四项各打0—2分：

- **H，Hook**：是否有反常识、冲突、数字、人物或时间窗口？
- **K，Knowledge**：读者能否获得新事实、新机制或新方法？
- **R，Resonance**：是否连接工作、赚钱、教育、隐私、尊严或普通人的选择？
- **O，Ownership**：是否有用户自己的经历、语料、系统或判断？

H/K/R至少两项得2分，O不得为0。

O为0时先补用户材料，不靠增加模仿口癖制造“活人感”。

## 四、建立证据台账

写之前把材料分成五类：

| 类别 | 可以怎么写 |
|---|---|
| A 一手事实 | 官方文档、模型卡、许可证、仓库、本人/公司原帖，可直接陈述明确内容 |
| B 平台口径 | 榜单、评测、产品接入，只能写成该平台在特定口径下的结果 |
| C 具名观点 | 可以证明某人提出了观点，不能证明政策或因果已经成立 |
| D 二次转述 | 只作为继续核查的线索，不作正文事实或逐字引语 |
| U 用户材料 | 用户录音原文、项目复盘和真实业务，可作为第一人称观点 |

涉及Get笔记时：

- 录音只读取 `data.note.audio.original`；
- 保持 `note_id`、`topic_id` 为字符串；
- 智能总结只用于定位，不替代逐字稿；
- 区分用户本人、第三方课程、访谈整理和既有加工成稿。

涉及公开阅读量时：

- 不把搜索排序、转载量、评论数或腾讯镜像读数冒充微信公众号后台阅读量；
- 写清平台、采集日期和口径。

## 五、只保留一条因果主线

用三句话定骨架：

1. **外部冲突**：谁与谁在争什么，为什么现在升级？
2. **读者后果**：这个变化会影响普通人的哪个选择？
3. **用户判断**：用户真正相信、并有材料支撑的结论是什么？

AI科技趋势文章优先使用：

`事件升级 → 技术门槛下降或入口变化 → 价值向数据、场景、分发和工作流迁移 → 普通人如何留下自己的资产`

删掉不能服务主线的知识点。研究量不等于正文信息量。

## 六、设计标题和开头

标题同时包含：

- 高识别对象；
- 具体冲突或反常变化；
- 对读者的后果。

可用公式：

`人物/产品 + 发生了什么 + 读者真正该关注什么`

开头约100个汉字内完成：

1. 一个具体时间、动作、结果或异常信号；
2. 一句升级判断；
3. 一个尚未解决的问题。

不要从“在这个时代”“随着技术发展”“最近很火”开始。

## 七、按证据阶梯写正文

默认推进顺序：

`真实触发 → 第一条反常证据 → 更多数据/截图/实测 → 机制解释 → 行业或人的处境 → 用户判断 → 行动`

趋势冲突型可用六拍：

1. 冷开场；
2. 三步时间线；
3. 异常缺席、利益错位或规则门槛；
4. 足以解释因果的技术和商业机制；
5. 从“他们在争什么”切回“我们在建设什么”；
6. 一至三个可执行动作。

控制节奏：

- 一段只承担一个动作或判断；
- 事实段稍长，判断段主动缩短；
- 中段安排两至三次小反转，不只靠标题；
- 术语后立即翻译成人话；
- 连续两段技术细节后，回到利益或真实场景；
- 小标题不是禁区：短文或强叙事可不用，教程、长文和移动端阅读可使用。

## 八、让用户而不是参考作者成为第一人称

读取 `references/user_voice.md` 后：

- 优先保留用户逐字稿里的判断、比喻、失败和犹豫；
- 轻清理口头填充词，不把原话抛光成整齐排比；
- 每个核心判断至少连接一个真实项目动作或结果；
- 没有亲历的事，不写成“我亲眼看见”“我早就判断”；
- 不使用参考作者的署名、邮箱、固定尾部、签名句或粗口词库；
- 不用连续的“我觉得”“说真的”等预制口语制造假活人感。

## 九、做事实、原创性和价值审计

### 事实

- 时间、参数、许可证、榜单和互动量是否有来源与时点？
- `open weights` 是否被误写成无条件完全开源？
- 公开指控是否被写成事实？
- 第三方评测是否被外推为通用能力结论？
- 分析判断是否明确属于作者判断？

### 原创性

- 是否复制参考文的标题结构、长句、笑话、比喻或段落顺序？
- 去掉人物名和参数后，文章是否仍有用户自己的核心判断？
- 是否用新的因果主线重组材料，而不只是逐段换词？

### 读者价值

- 读者看完学到了哪个新事实或机制？
- 他能立即做哪一件事？
- 结尾是否从前文自然长出来，而不是硬升到“时代、文明、人性”？

## 十、分阶段交付

### Phase A，文字

- 只创建或更新一个正文Markdown；
- 保留一个H1；
- 不放图片占位符、TODO、内部证据日志；
- 跑确定性校验；
- 等待用户修改或明确“文字定稿”。

### Phase B，图片与发布包

只有用户明确“文字定稿”“文案没问题，可以做图”或同等确认后：

- 冻结正文；
- 回到官方页面和X原帖重新核对动态数据；
- 制作截图、封面和HTML；
- 保留账号、时间、Logo、图表署名和第三方水印；
- 不用生成图冒充真实页面；
- 仅在用户明确要求同步或归档，并能从当前对话唯一确定目标知识库后写回Get笔记；
- “定稿”只开放图片和发布包，不自动授权外部写入；
- 用户本轮提出归档要求时，最终交付报告归档状态：已同步并验证，或尚未同步及其原因。

### Get笔记归档闭环

笔记接入使用安装者自行配置并授权的连接器。缺少连接器时读取本地导出的原始 Markdown/逐字稿并交付本地文件；不能要求安装任何未列明的私人 Skill。本节给出完整归档闭环，按当前服务实际 API 对应实现。

用户明确要求同步后，按以下顺序执行，不得把其中任一步当成完整成功：

1. 重新读取最终Markdown，提取H1为笔记标题，移除封面、正文图片引用和本地路径；保留用户批准的正文与结尾，不写入HTML、事实台账、发布说明或内部证据日志。
2. 调用自有知识库列表，按名称精确匹配目标知识库；名称缺失或存在歧义时停止并询问，不创建替代知识库。
3. 分页读取目标知识库笔记，按完整标题和正文去重。
4. 标题和正文完全相同时，不重复创建，直接回读并报告已有笔记。
5. 同标题但正文不同时，不静默覆盖；先向用户说明差异，再取得更新原笔记或另建版本的明确选择。
6. 无重复时创建 `plain_text` 笔记，将API返回的 `note_id` 始终作为字符串处理。
7. 用 `knowledge/note/batch-add` 把该 `note_id` 加入精确的字符串 `topic_id`。
8. 回读笔记详情，并分页检查目标知识库成员关系；只有标题、正文和知识库归属全部确认后，才能报告“已同步”。
9. 遇到限流时遵循 `retry_after`；任何API失败都报告真实错误，不伪造成功。

## 十一、运行确定性校验

基础校验（若安装者提供了固定结尾，追加 `--cta-file CTA.txt`；没有配置则不强制 CTA）：

```powershell
python -X utf8 scripts/validate_article.py --input ARTICLE.md --max-chars 1800
```

有参考原文时追加查重：

```powershell
python -X utf8 scripts/validate_article.py --input ARTICLE.md --max-chars 1800 --reference SOURCE.md --strict-overlap
```

脚本失败时先修正文，再报告结果。不要为了通过扫描而恢复参考作者的措辞。

## 十二、终审输出

交付时简要说明：

- 使用了哪些一手来源和用户材料；
- 哪些动态数字或第三方说法被降级、删除或保留归因；
- 字数与校验结果；
- 当前是否仍处于文字阶段；
- 图片和HTML是否已经生成；
- 用户本轮要求归档时，报告目标知识库、同步状态、`note_id`和回读验证结果；未执行时明确写“尚未同步”。

## 停止条件

- 无法读取原文时，不声称完成全文研究；
- 无法核实公众号后台阅读量时，不声称“真实Top 30”；
- 用户材料不足时，不伪造第一人称；
- 不把具体在世作者的独特表达做成可调用短语库；
- 不移除第三方署名或水印；
- 未获文字批准，不制作最终图片、HTML或执行外部归档。
- 未完成笔记详情和知识库成员关系双重回读，不声称Get笔记同步成功。
