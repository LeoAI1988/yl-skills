# 开拍画质与自然肤色收尾

开拍增强是剪辑审核通过后的最后一步；**半自动**须先获得用户对完整逐字稿方案的确认，完成剪辑后交付未开拍增强版，再获得用户对剪辑版的确认，才调用 API；**全自动**由执行者完成内部审核后直接继续本次范围内的增强及最终验收，不增加中间确认。按 [入口模式选择规则](../SKILL.md) 记录本次模式：新剪辑任务未指定先问，全程沿用已选模式，不能凭“开始／剪一下”默认全自动。仅修改 Skill 或回答问题不触发模式提问或 API 调用。入口为 `scripts/kaipai_enhance.py`，安装者须自行取得官方 SDK，通过 `--sdk-dir` 或 `KAIPAI_SDK_DIR` 指定包含 `__init__.py` 和 `core/` 的 SDK 目录，再由包装脚本以 `sdk` 别名加载；本分享包不再分发未附许可文件的第三方 SDK，详见 [安装与依赖](approved-example.md)。目标是自然肤色、清晰细节和稳定播放；API 成功、码率提高或输出 4K 都不等于画质通过。

## 版本与授权

- 以实际确认记录、EDL、字幕、音轨、输出时间和哈希确定版本，不按 v2/v3 大小推断新旧。
- 画质、美颜或接入调试只修改授权部分，冻结内容、字幕时轴、标题、速度及原声。不为此重新走逐字稿审批，也不能拿另一条时间轴的旧增强片替代。
- 按 [入口执行方式](../SKILL.md) 通过 GATE-2：半自动必须记录用户对本轮“剪辑完成、未做开拍增强”版本的确认；仅确认逐字稿、旧版或表达稍后会看，不算通过。全自动由执行者完成剪辑审核后继续本次范围内的增强，不再索要中间确认。两模式均需先剪净无信息停顿，待处理为零；不能用开拍掩盖未剪完的时间轴。用户明确“先不要开拍”时遵守。用户明确授权某片 API 调试/测试时，可以完成该片短样与必要的完整测试，不重复索要已有授权，不扩展成批量。

## 色彩链路

1. 探测原片 primaries、transfer、matrix、range、位深与旋转。HLG BT.2020 按 [渲染与画质](rendering.md) 做真实 HDR→SDR；SDR BT.709 走保真通路。位深仅作线索，错误转码会留下 8-bit HLG，不能猜贴标签。
2. **转换在叠字幕之前**。从原片按本条 EDL 转换，完成剪辑与文字层后得到干净 SDR 剪辑版。普通剪切与 hook 重排都须经过转换。已烤字幕的错误 HDR/混合成片应回原片重导，不整帧 tone map。
3. 上传前检查实际码流/解码帧为 BT.709 原色、传递、矩阵，limited 范围，且 MP4 视频轨 `colr` 为 nclx 1/1/1、limited。只有 nclc 而没有明确范围的文件先核实并规范封装。只写 `-color_trc bt709`、只跑 `h264_metadata` 或只看 `ffprobe -show_streams` 不够。包装脚本拒绝混杂/未知输入，修好后才提交。
4. API 原始输出独立保存，再做相同色彩检查，核对时长、帧率、方向和构图。API 可改变分辨率、声音编码和局部细节，不假定原样。
5. 只有输入记录、转换命令与同帧像素共同证明“像素已是正确 SDR，仅元数据错”时，才允许单独修标签；须同时修好容器与码流并回读。**HLG 转换遗漏不能靠改标签修复。**

典型故障：HLG 原片错误地按 SDR 导出，留下 709 矩阵 + 2020 原色 + HLG 传递；随后只修 SPS 又可能留下容器 colr 与码流冲突。不能统一改标签，须核对真实像素转换及三层标记。

## API 能力与自然美颜

2026-09-14 实时配置中 `hdvideoallinone` 为 `/v1/hdvideoallinone_async`、`params={}`，没有暴露磨皮、瘦脸、肤色或强度参数。能力变化时重新读取任务预设/正式文档；不能猜强度参数，也不能把 HTTP 成功当作参数生效。`image_restoration` 的 `parameter.use_hd_face_opt` 属于图片，不能套给视频或逐帧调用制造闪烁。

- **默认不加额外色彩滤镜**：停用旧 `--brighten` 以及固定 `eq=brightness=0.025:saturation=1.045,colorbalance=rs=-0.04:bs=0.04`。后者调整暗部色彩，不是中性白平衡；也不固定加 gamma 或饱和度。
- “明亮白皙/冷白”以自然观感验收，不机械减红加蓝。白衣、灰物保持中性；肤色保留血色、阴影和纹理，不灰青、过白、过曝或蜡像感。
- 新接入、源类型或参数改变时，先用本片几秒正常光和运动样本跑真实 API，对照正确 SDR 基底后再处理完整确认版。同条件已通过的证据可复用，不机械地每片多烧一轮。
- 正确输入下若仍重磨皮或脸型/镜框变形，记录当前视频任务没有公开力度控制的限制。未经时空配准，不将原片与增强片简单透明度混合，避免重影。必要时交付自然 SDR 版与增强测试版作对照，不能用偏色滤镜掩盖模型问题。

## 调用、保存与续查

凭证只读取 `MT_AK/MT_SK` 环境变量，或用户显式通过 `--env-file` 指定的文件。不会向上遍历目录或读取作者机器的默认配置。不要把真实凭证写入 Skill、命令行参数、报告或仓库；不输出签名结果 URL。视频输入用已探测的本地文件。

```powershell
python -X utf8 scripts/kaipai_enhance.py --task hdvideoallinone --input "./work/approved_sdr.mp4" --out "./work/kaipai_raw.mp4" --ffprobe "ffprobe"
```

- checkpoint 默认 `<out>.kaipai.json`，可用 `--checkpoint` 指定。提交回调立即保存 task_id、输入哈希、任务与实际参数；异步超时用原 task_id 续查。已有输出/checkpoint 不重新 execute；下载或本地验证失败不重复消费。重剪/变参使用新版本和新的请求记录。
- 下载先写临时文件，成功后改名；API raw 不被提亮、调色或成品封装覆盖。技术通过仍为 `pending_visual_review`，不能当美颜通过。
- 续查：`python -X utf8 scripts/kaipai_enhance.py --task hdvideoallinone --task-id "已有ID" --out "原raw路径" --ffprobe "ffprobe"`。沿用原 checkpoint，状态不明先查，不再提交。
- 退出码：0=raw 技术通过但待视觉检查；2=可恢复/待续查；3=needs_review；1=拒绝/失败。`--brighten` 明确拒绝；当前视频任务不接受无文档的非空 `--params`。
- 使用当前安装者的 Python 3.10+；FFmpeg/FFprobe 优先从 PATH 读取或通过参数指定，其他参数以 `--help` 为准。

## 最终封装与验收

API 可能重编码声音。将合格 raw 视频与**原剪辑版 AAC**无损封装为新成品，只有一条视频、一条原声；验证帧数、完整声音、时长和同步。色彩正确且规格可用时不再编码、不再调色；按用户规格缩放时，从 raw 只做一次高质量编码，保留母带。

若 API 仅调整了显示末帧包时长，使平均帧率和视频总时长出现小偏差，先保留严格失败报告。只有完整解码帧数与全包 PTS/DTS 证明 CFR 排布未变时，才按 [验收规则·API 末包时长舍入](acceptance.md#api-末包时长舍入的显式例外) 使用 Python 验收器的 `--allow-end-packet-rounding`；显式提供本片 `--fps --frames --duration`。不重新编码视频或改写时间戳来消除单纯封装末包差，也不凭“小于一帧”直接放行。

对照首段、标题退场、普通光、逆光/高光、运动与结尾。查看同源同刻的正确 SDR 基底、API raw 和成品，兼看自然尺寸与100%人脸局部：肤色、眼镜、发丝、衣纹、背景、白黄字幕分别核对。均值/高光统计只辅助诊断，天空和白字幕的高光不能当成人脸过曝。API 可能改字、涂抹字幕或几何变形，不能预先保证不会。没有实际播放器测试就如实记录，不据抽帧声称验证了 Windows 播放器。

记录输入/输出哈希、转换链、task_id、实际参数、音轨验证、色彩三层检查、同帧对照及用户审核状态。按 [验收规则](acceptance.md) 分项交付，保留旧视频与通过封面。同一口播的视觉版本共用完整稿，不重复云端入库；新测试版待用户确认后按归档规则处理。

回片旋转异常先按 [规范化与增强回片](final-review.md#规范化与增强回片) 区分真实像素方向和显示元数据；不盲目旋转、不先重复提交增强。
